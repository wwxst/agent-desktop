# Agent Desktop 六项运行时能力分阶段实施手册

日期：2026-09-23。状态：执行手册，尚未实施。

本手册供其他软件或开发者逐项实施使用，不代表任何能力已经存在。本手册只授权执行方实施用户本次明确指定的单一阶段；阶段完成后必须停止并汇报，不自动进入下一阶段。需要继续时，由用户另行指定下一阶段。

## 1. 权威来源与实施顺序

技术设计以[六项能力设计方案](./2026-09-23-agent-runtime-six-capabilities-design.md)为唯一详细来源。本手册只规定实施拆分、授权边界、执行步骤、验收和交付格式；两者冲突时先停止并报告冲突，不自行选择或改写设计。

```text
ID     Design section  Capability                         Prerequisite
P1     第 1 项          命令审批、实时输出和取消             核对工作树与功能分支基线
P2     第 2 项          执行中提问并继续当前轮次             串行工具调用与审批行为正确
P3     第 5 项          真实过程说明                         复用真实模型公开文本和活动投影
P4     第 3 项          视频结果检查与候选发布               候选验收/发布设计可用并已核对
P5     第 4 项          有限模型请求重试                     不重放已完成工具，分类和预算一致
P6A    第 6 项 A        只读子智能体                         父子身份隔离、取消和进度可用
P6B    第 6 项 B        应用运行期间的持久终端               P1 权限与进程回收已真实验收
```

推荐顺序为 `P1 → P2 → P5 → P3 → P4 → P6A/P6B`，与总设计的依赖和风险排序一致。P6A 与 P6B 彼此独立；P6B 不得因 P6A 未实施而等待。不能因为阶段编号相邻就假定前置能力已完成，执行方必须检查代码、测试、文档和真实运行证据。

## 2. 所有阶段通用的执行约定

### 2.1 仓库和工作区

开始任何阶段前，先阅读根目录 `AGENTS.md`、`docs/engineering.md`、`docs/architecture.md`、`docs/defensive-patterns.md` 和本手册引用的设计方案；检查 `rg --files -g AGENTS.md` 的结果，确认受影响目录没有额外规则。涉及桌面界面时，必须完整阅读 `.agents/skills/desktop-frontend/SKILL.md`，并以 `docs/desktop-ui.md` 为界面行为的唯一文档来源。

先记录仓库路径、分支、HEAD、`git status --short --branch` 和与本阶段有关的现有 diff。工作树有未提交改动时，逐项判断归属和重叠范围；不得重置、清理、覆盖、暂存或提交不属于本阶段的改动。若无法在保留现有改动的同时得到清晰基线，停止并请用户决定隔离方式。新增能力按 `docs/engineering.md` 使用功能分支，不直接在 `main` 开发。

本手册创建时的工作树状态不属于实施基线。执行方必须在每个阶段重新检查当前分支、HEAD、工作树和设计状态，不能把本手册创建时的状态当成当前事实。

### 2.2 每阶段固定边界

- 只实施用户指定的一阶段和设计方案中该阶段的最小生产调用链，不提前建立后续阶段接口、按钮、配置、依赖或占位实现。
- 先核对当前源码、实际入口、生产消费者和测试，再编码。计划文档不是实现证据。
- 不把 Agent Core（智能体核心）与 UI（用户界面）逻辑混合；不把具体 Provider（模型供应商适配器）或 Tool（工具实现）塞入核心循环；不新增无真实消费者的抽象。
- 遵守最小实现规范与防御性规则；仅在真实外部边界校验输入，不以兜底掩盖程序错误。
- 修改源码和行为文档时，保持二者同步。文档只记录本阶段稳定事实；本手册仍作为执行导航，不复制成为新的 Current Truth（当前事实）。
- 不自动创建下一阶段分支、不实施下一阶段、不提交到 `main`、不合并、不推送、不创建发布物。提交或合并按项目流程另行由用户授权。

### 2.3 验证与失败口径

按 `docs/engineering.md` 的工程基线执行本阶段所需验证。完整自动化门禁为：

```powershell
corepack pnpm install --frozen-lockfile
corepack pnpm check
```

功能阶段按工程基线执行这两个统一门禁；如果当前环境不允许安装或锁文件校验，必须报告具体阻塞。按变更范围再选择并执行需要的桌面构建、浏览器端到端或真实应用验收。命令、模型、视频、原生终端等真实边界必须有对应真实链路证据；浏览器模拟、单元测试和构建不能替代真实进程或真实服务验收。

```text
PASS   通过       已运行且有可复核证据，达到本阶段退出条件。
FAIL   失败       已运行但结果不符合要求，或承诺的验证环境缺少必需配置。
SKIP   跳过       未运行，并写明具体原因、未覆盖范围和风险；不算验收通过。仅本地缺少可选外部条件时使用；承诺存在配置的验证环境缺配置应判 FAIL。
N/A    不适用     该验证与本阶段无关，并简述依据。
```

必须区分已实施、自动化验证、真实链路验证和已集成。当前本手册不授权提交或合并，因此阶段完成不等于已集成到 `main`。

### 2.4 阶段交付报告

完成或停止时，用以下格式报告事实：

```text
阶段：
分支 / HEAD：
变更文件与行为：
未实施范围：
自动化验证：命令、PASS/FAIL/SKIP 与结果
真实验收：输入、环境、结果和证据；不适用时说明原因
Review：发现、修正、Decision（PASS / CHANGES_REQUIRED）
残余风险 / 阻塞：
集成状态：未提交 / 已提交到功能分支 / 其他（需有证据）
下一步：停止并等待用户指定阶段
```

## 3. P1 命令审批、实时输出和取消

### 执行范围

按设计方案第 4 节实施从模型工具调用、逐命令审批、Windows 非交互 PowerShell 子进程、有限实时输出、取消与关闭收尾，到历史展示的完整闭环。必须准确告知这是以当前用户权限执行的本机命令；工作目录不是操作系统沙箱。已有专用视频和文件工具继续保留，不被通用命令取代。

影响面以真实调用链为准，预计包含工具执行上下文、Agent Loop（智能体循环）的进度转发、应用层注册、Desktop Main（桌面主进程）的审批和子进程生命周期、IPC（进程间通信）、Shared Client（共享客户端）展示及会话快照。不要为了方便把进程调用放进 Renderer（渲染进程）或 Agent Core。

### 执行步骤

1. 逐项确认设计方案中 `run_command` 输入、审批事实、环境变量边界、输出限额、超时、错误结果、进程树取消与恢复保证；若实现技术与设计不符，先停下报告。
2. 先写当前生产调用链和改动清单，再实现最短端到端路径；进度回调同步入队，不等待 UI，不写入诊断追踪或模型上下文。
3. 为批准、拒绝、过期审批、启动失败、非零退出、超时、输出截断、取消和窗口关闭增加契约测试。
4. 运行真实 Windows 进程验收，至少验证 PowerShell → `.cmd` → Node 孙进程，并检查停止与关闭后后代进程实际已退出。
5. 验证历史可读、重启不重放命令，并回归现有视频、普通问答、文件读取和已有文件审批。

### 阶段退出条件

批准前没有进程启动；执行命令与审批卡所示一致且只运行一次；双流输出来源可辨、界面和缓存有界；非零退出、超时和取消不伪装成功；支持的进程树确实回收；恢复只还原有界历史，不重放命令；相关自动化与真实验收达到 PASS。任一真实进程或安全语义验收为 SKIP 时不得报告阶段完成。

### 可复制执行指令

```text
仅实施本手册 P1“命令审批、实时输出和取消”。先检查当前仓库、分支、HEAD、工作树改动及所有相关规则；保留全部既有改动。以 docs/superpowers/plans/2026-09-23-agent-runtime-six-capabilities-design.md 第 4 节为技术依据，仅改 P1 必需的最小生产调用链，不实现 P2–P6，不提交、合并或推送。完成设计核对、自动化测试、真实 Windows 进程树验收和 Review；缺少必需真实验收不得标为完成。完成后按执行手册 2.4 汇报并停止，等待用户指定下一阶段。
```

## 4. P2 执行中提问并继续当前轮次

### 执行范围

按设计方案第 5 节，在模型确实需要用户信息时，通过提问工具和输入框上方的问题卡等待答复，然后在同一 `turnId`（轮次标识）内继续。答案或跳过作为工具结果进入会话；关闭或停止使用明确的关闭事实；未完成 Step（步骤）不得进入恢复后的模型上下文。问题卡不得借用主输入框或绕过后续命令/文件审批。

### 执行步骤

1. 确认当前工具串行执行、工具结果写入 Session（会话）和任务取消的实际语义。
2. 实现 `ask_user` 的当前应用层消费者、待决问题的宿主状态和最小 IPC/客户端接口；不为一个工具新增包或通用工作流框架。
3. 实现自由文本、可选项、跳过、重复/迟到答复拒绝、停止和窗口关闭；关闭事件可供历史展示但不进入模型恢复上下文。
4. 验证真实 Agent Loop 下一次模型请求包含答案，且同轮继续、已完成工具不重跑。
5. 验证旧快照没有可操作的问题、主输入草稿与普通发送/审批行为不受影响。

### 阶段退出条件

答复前后 `turnId` 一致；选择、自定义答复、跳过、停止、关闭和重复答复行为都有明确测试；答案是真实下一次模型上下文的一部分；已完成工具不会重跑；恢复不会产生可操作的陈旧问题卡；界面通过实际交互验收。

### 可复制执行指令

```text
仅实施本手册 P2“执行中提问并继续当前轮次”。先确认 P1 或等价的现有审批/取消基础仍正确，但不要顺便修改 P1。以六项设计方案第 5 节为依据，只增加 ask_user 当前生产消费者及必要宿主、会话、IPC 和界面闭环；不实现其他阶段，不提交、合并或推送。验证答案进入同一轮下一次模型请求、跳过/停止/关闭/迟到答复及恢复行为。按执行手册 2.4 汇报并停止。
```

## 5. P3 真实过程说明

### 执行范围

按设计方案第 8 节，将模型真实产生、且完整响应中伴随工具调用的公开文字作为过程说明，按 `stepId`（步骤标识）与真实工具顺序显示；最终答复仍只显示一次。不得展示模型内部推理，不得伪造播报，不新增专用模型调用或供应商推理字段。

### 执行步骤

1. 检查现有 `delta.content`、完整 `ModelResponse.text`、Session 事件和活动投影，确认真实信息来源。
2. 为步骤增量和确认后的过程文字建立最小必要关联；增量未完成时保持临时态，完整消息确认用途后只投影一次。
3. 复用既有活动列表和样式，保证过程说明排在其工具调用之前，不创建第二套顺序状态。
4. 覆盖多步骤工具往返、最终答复、空文本、中途失败/取消和历史恢复。

### 阶段退出条件

过程文字来自真实完整模型响应；步骤顺序正确；最终回答不重复；无文字时没有空节点；失败/取消仅保留已确认内容；历史恢复不补造内容；普通问答不多出过程行；没有内部推理正文。

### 可复制执行指令

```text
仅实施本手册 P3“真实过程说明”。以六项设计方案第 8 节为依据，沿用模型公开 text 和现有活动列表；禁止展示内部推理、编造说明、增加播报请求或建立第二套活动顺序。先核对当前事件与快照真实来源，只改本阶段所需模块。验证多步工具往返、最终答复去重、失败/取消和历史恢复；按需使用 desktop-frontend 技能。完成后按执行手册 2.4 汇报并停止，不实施 P4 或后续阶段。
```

## 6. P4 视频结果检查与候选发布

### 进入条件

本阶段依赖[候选验收与发布设计](./2026-09-22-output-item-candidate-validation-published-output-design.md)。先检查该设计文档在本次执行基线上是否存在、状态是否已复核，以及现有源码是否已经有对应生产能力。设计建议接口不等于已实施接口；若设计无法取得、边界冲突或候选/发布实现基础缺失，停止并报告，不自行补造范围。

### 执行范围

按六项设计方案第 6 节，仅把视频候选作为正式结果检查消费者；检查结果必须引用实际候选和工具证据。完成语义需要联合实现声明、候选生成、逐项验收与发布，不得把 `turn.completed`、退出码 0、模型自述或单个检查卡当作交付成功。首期不为普通代码/文本任务创建通用 Review（结果检查）通过状态。

### 执行步骤

1. 核对现有视频输出、不可覆盖规则、媒体检查、视觉/语音证据、活动投影及候选设计，记录缺口和真实消费者。
2. 按输出项分别关联候选、要求、验收项和发布结果；由应用层核对证据，UI 只展示真实结果，不自行判定 `passed`。
3. 补足全文件解码等设计中承诺的真实检查；证据不足应为 `blocked`（无法确认），不能算通过。
4. 确保不合格或身份不匹配的候选不发布；生成修正版必须成为新候选并重新验收；已发布结果不因后续取消被谎报撤回。
5. 用真实视频输入跑完生成、检查、发布及独立复测，并逐项对照界面状态。

### 阶段退出条件

候选身份与证据匹配；缺少证据显示无法确认；不合格候选不发布；多输出逐项核对；复制/发布失败不登记为产物；真实成片独立复测与 UI 一致。真实视频链路未 PASS 时不能宣布交付闭环完成。

### 可复制执行指令

```text
仅实施本手册 P4“视频结果检查与候选发布”。开始前确认 docs/superpowers/plans/2026-09-22-output-item-candidate-validation-published-output-design.md 在当前基线可用，并核对其设计状态和现有生产实现；缺失或有冲突则停止报告。随后以六项设计方案第 6 节为依据，只实施视频候选的声明、证据验收、发布和真实展示，不建立通用代码/文本 Review。必须用真实视频完成独立复测；缺真实条件标 SKIP 且不得宣称阶段通过。按执行手册 2.4 汇报并停止。
```

## 7. P5 有限模型请求重试

### 执行范围

按设计方案第 7 节，仅为真实 DeepSeek 模型请求实现分类、有限次数和可取消等待。Provider（供应商适配器）把外部错误映射为供应商无关的 `ModelRequestError`；Agent Loop 根据该通用分类执行每 Step 和每 Turn 的预算。命令、文件写入、视频生成、发布及已完成 Tool 不自动重放。

### 执行步骤

1. 阅读当前 DeepSeek 流式请求生命周期与模型接口，标出首次产生可见文本/工具调用之前后的分界。
2. 在 Provider 边界分类 HTTP 429、502、503、504 和已识别临时连接错误；认证、参数、协议、取消、部分流和长度上限失败不可重试。
3. 在循环中集中计数并等待；实现每 Step 最多一次重试、每 Turn 最多两次额外请求、服务端 Retry-After 等待上限与取消传播。
4. 产生可审计的 `model.retrying` 事实，不新建 Step、不追加失败 assistant 消息、不重复之前工具。
5. 用受控测试覆盖状态分类和预算；使用真实模型链路验证可用环境下的一次真实成功请求。不得人为制造外部服务不稳定并声称真实服务故障覆盖。

### 阶段退出条件

临时失败按预算重试；认证/参数/协议/取消/部分流不重试；等待期间取消不发新请求；Turn 预算累计正确；失败请求不产生可执行工具或重复文本；已完成工具不重放；追踪不写响应正文或凭据。

### 可复制执行指令

```text
仅实施本手册 P5“有限模型请求重试”。以六项设计方案第 7 节为准，在 DeepSeek Provider 做外部错误映射，在 Agent Loop 做唯一预算控制；不得包裹/重跑整个已执行 Turn，不重试工具或部分流。覆盖 429/502/503/504、401、协议错误、取消、Retry-After、Step/Turn 预算及已完成工具不重放。真实模型链路缺条件须明确 SKIP，不能伪装 PASS。完成后按执行手册 2.4 汇报并停止。
```

## 8. P6A 受限只读子智能体

### 执行范围

按设计方案第 9.1 节，仅支持父任务明确委派的一层只读子任务。Desktop 注入 `DelegateTasksPort`（委派任务端口），子智能体使用独立 Session 和明确的只读工具列表，不注册递归委派、写文件、命令、终端或审批工具。首期最多两个并行任务；限制必须在生产入口真实执行，不只写进系统提示。

### 执行步骤

1. 确认父 Agent 的 `AbortSignal`、Session 隔离、文件工具目录语义、实时活动投影及可用模型配置。
2. 在应用层实现端口和唯一真实消费者；核心循环不依赖子智能体实现，委派工具不导入 Provider 或读取密钥。
3. 创建最小子任务上下文，不复制父会话全部历史；把子任务事件嵌套到父工具活动而非父模型步骤。
4. 覆盖两个子任务结果隔离、一个失败另一个成功、深度/数量/步骤/时间预算、父取消等待全部收尾和历史关联。
5. 验证只读工具注册集合与真实文件访问边界；核对实际请求数和成本影响。

### 阶段退出条件

最多两项且不能递归；没有写入和命令能力；子会话与父会话隔离；单个失败不丢弃其他结果；父取消后无遗留请求；预算耗尽明确显示未完成；父子关系可追溯；有真实模型与工具运行证据。

### 可复制执行指令

```text
仅实施本手册 P6A“受限只读子智能体”。以六项设计方案第 9.1 节为依据，由 Desktop 应用层注入 DelegateTasksPort；子任务独立 Session、仅注册指定只读文件工具、不注册 delegate_tasks，深度一层且每轮最多两个。先核实当前生产文件边界和取消生命周期。不得做后台任务、跨重启续跑、自动合并或写入。验证真实子任务、父取消后无遗留请求、预算和父子历史关系。按执行手册 2.4 汇报并停止。
```

## 9. P6B 应用运行期间的持久终端

### 进入条件

必须先确认 P1 命令权限、审批展示和进程树回收已通过真实 Windows 验收。若 P1 未实施、未通过或证据不可用，停止本阶段。实施前先独立验证 Windows ConPTY（Windows 伪终端）、Electron ABI（应用二进制接口）、原生依赖构建和打包能力；验证失败时不安装正式依赖、不搭空壳 UI，提交验证结果并停止。

### 执行范围

按设计方案第 9.2 节，终端只在当前应用进程和会话中持久。Desktop Main 按 `sessionId + terminalId` 持有进程状态；跨应用重启只恢复有界输出历史并显示 disconnected（连接已结束），不恢复句柄、不按 PID 重连、不重跑命令。模型每次向交互终端发送输入都展示准确内容并逐次审批；批准启动 shell 不代表永久授权后续输入。

### 执行步骤

1. 完成原生终端最小可行性验证，并记录 Electron 版本、Node ABI、原生包构建/打包、中文与进程关闭证据。
2. 只在验证通过后按工程规范固定必要依赖；明确每个新增依赖的唯一职责及真实消费者。
3. 在 Desktop Main 按会话持有资源，加入 `open_terminal`、`read_terminal`、`write_terminal`、`close_terminal` 的最小实际消费者及归属校验。
4. 区分独立终端运行状态与已完成 Turn；为输出和快照设上限；删除会话、停止所属任务和正常关闭时回收资源。
5. 真实启动本地开发服务；测试跨轮复用、跨会话拒绝写入、逐次审批、中文/控制序列、停止和关闭进程回收，以及重启后 disconnected 且不重跑。

### 阶段退出条件

原生模块在目标桌面环境稳定构建和打包；同会话可跨轮读取，其他会话不能操控；每次输入审批；进程树和宿主资源实际回收；快照不含 PID/句柄且恢复不伪装运行；真实服务启动、读取、停止链路通过。缺少任一关键原生或生命周期证据不得报告完成。

### 可复制执行指令

```text
仅实施本手册 P6B“应用运行期间的持久终端”。先证明 P1 命令权限和进程树回收真实验收通过；再独立验证 ConPTY、Electron ABI、原生模块构建/打包、中文和进程关闭。验证失败就停止，不加依赖或占位界面。通过后仅在 Desktop Main 实现按 sessionId + terminalId 持有的终端资源；逐次审批输入，快照只存有界历史，重启统一为 disconnected 且不得重跑。按执行手册 2.4 汇报并停止。
```

## 10. 全部阶段完成的定义

本手册列出七个可独立授权的实施阶段，对应用户讨论的六项能力；子智能体与持久终端是第六项的两个不同交付。整体计划只有在各阶段分别获得授权并逐项完成后才算实现。不得用一个阶段的通过推断其他阶段完成，也不得用演示数据、静态卡片、假工具事件或总方案文档替代生产调用链和验收证据。
