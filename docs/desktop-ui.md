本文是 `apps/desktop/src/renderer/**` 当前视觉设计与验收要求的权威文档。它记录已经通过真实页面对照和渲染层实现确认的界面事实，不定义智能体、进程通信、会话或媒体处理行为。

## 目标与范围

当前界面服务多视频、单任务的视频剪辑闭环。设计目标是安静、紧凑、可扫描的智能体工作区，让主要注意力落在任务、执行过程和产物上，而不是品牌栏或装饰。

当前不实现多轮历史、工作区切换、模型或模式选择、预览版标签、任务队列、播放器、时间轴、拖拽、新附件类型或通用界面组件库。侧栏只展示当前 Agent Desktop、视频剪辑工作区和当前任务，不承担 DSH 会话管理功能。空状态不得演变成欢迎营销页，也不得复制参考产品的品牌与产品概念。

## 当前实现事实

以下内容以当前 Renderer（渲染层）和 Electron Main（主进程）代码为准，是此前视觉对照和交互讨论已经确认并落地的结果。

```text

Sidebar               工作区侧栏        以纯文字 Agent Desktop 品牌行、视频剪辑、当前任务和本地运行状态展示当前上下文，不提供 DSH 会话管理。

Attachment            附件              视频可选；有一个或多个视频时显示 DeepSeek Harness（参考客户端，DSH）文件卡片轨道，无视频时不渲染空附件。
```

### 页面骨架

- 桌面布局采用“侧栏 + 主工作区”两栏关系。侧栏是上下文锚点，主工作区承担对话和任务执行。
- 主工作区内部是可滚动对话区和 Composer；不保留独立顶部栏或顶部预留空间。
- 默认窗口和窄窗口都保持同一层级；窄窗口只收缩侧栏图标，不把侧栏整体删除，避免顶栏变成孤立卡片。

### 顶部栏

- 当前不显示独立顶部栏；页面顶部不保留空白占位。
- 工作区名称、当前任务和本地运行状态统一由侧栏承担。

### Composer 与发送契约

- 发送按钮使用 34px 圆形蓝色主操作，箭头是 18px SVG 图形，不使用 Unicode 字符。
- 输入框为空时，发送按钮必须保留 `disabled`；处理中也必须禁用。
- 禁用发送按钮使用默认指针，不显示 `not-allowed`，不制造“可执行但失败”的交互暗示。
- 只要有任务文本，即使没有选择视频也可以发送；这时用户消息不显示附件，主进程向 Agent 发送纯文本任务提示。
- 只有视频没有任务文本时仍不可发送，因为当前 Desktop IPC（桌面进程通信）任务契约要求非空文本。
- “就绪”状态不常驻显示；处理中只在发送按钮旁显示“处理中”。
- 附件 `+` 按钮保留键盘可达性，但不显示额外蓝色焦点外圈。

### 无视频任务边界

- Renderer 允许无视频提交有文字的任务。
- Main 不再把选择视频作为所有任务的前置条件；无视频时不虚构输入视频和输出视频路径。
- `buildAgentPrompt` 在无视频时明确告诉 Agent 只回答文字需求，不调用需要媒体文件的 Tool，也不声称生成视频。
- `createVideoAgent` 在没有语音模型路径时不注册 `transcribe_audio`；选择视频后仍按现有视频任务配置要求语音模型。
- 有视频的剪辑任务仍沿用原有输出路径、工具追踪和产物展示链路。

## 强制规则与不能做

### 强制规则

- 视觉修改必须保持侧栏、中央对话轴和底部 Composer 的空间关系。
- 空状态和活跃对话必须使用同一个 Composer；切换时不能丢失草稿或重建输入节点。
- 所有发送状态必须遵守“空文本禁用、处理中禁用、有文字无视频可发送”。
- 视觉参考只用于尺寸、间距、密度和层级对照；实际功能仍以当前代码和视频 Agent MVP 为准。
- 修改 Renderer 后使用 `corepack pnpm desktop:dev` 进行实时视觉验收；修改 Main 或 Preload 后重启开发进程。

### 不能做

- 不能因为参考图增加 DSH 的工作区选择、会话列表、搜索、设置、模型选择、权限选择、轨迹页、Token 统计、日志下载或播放器。
- 不能恢复独立顶部栏、Logo 或品牌副标题；也不能仅因参考图出现搜索、通知等图标就加入没有真实业务行为的控件。
- 不能把省略号、侧栏工作区名称或状态图标做成没有真实消费者的按钮。
- 不能把无视频任务重新改回“必须选择视频”；也不能把空文本发送改成看起来可提交。
- 不能用大面积空卡片、渐变、品牌插画或高权重 Header 抢占对话区注意力。
- 不能把用户消息和 Agent 回复都做成对称气泡；Agent 回复保持平面正文，工具过程保持紧凑摘要。

### 明确禁止项

- 禁止把参考截图中的工作区选择、模式选择、预览版标签、品牌标题、模型选择器、插件入口或其他产品概念加入当前客户端。
- 禁止复制 DeepSeek Harness 的插件、插槽、状态存储、工作区运行时、子智能体运行时、技能运行时或其他架构；这里只吸收可验证的空间关系和交互层级。
- 禁止为了让截图更像而新增没有真实业务消费者的按钮、菜单、附件类型、状态文案或空壳能力；Composer 中的附件取消按钮具有真实移除行为，不属于空壳控件。
- 禁止把空状态做成营销页、独立欢迎面板或第二套输入区；Composer 必须是当前唯一的任务输入入口。
- 发送按钮在空文本或任务处理中保持 `disabled`；没有选择视频但有文字时仍可发送。
- 发送按钮禁用时使用默认指针，不显示 `not-allowed` 禁止符号。
- 禁止给附件 `+` 按钮增加蓝色焦点外圈；它保留键盘可达性，但不使用高权重蓝色装饰圈。

## 页面结构

### 空对话

- 尚无用户任务、工具活动、智能体回复或错误时，欢迎内容与现有输入区组成一个整体，位于主工作区视觉中心。
- 空状态只显示“开始一个视频任务”和“选择视频，或者直接告诉 Agent 你想做什么。”，输入区仍是首要操作；不显示示例任务、推荐任务或快捷指令。
- 用户发送首个任务后，空状态整体消失；对话内容进入阅读轴，同一个输入区切换到底部停靠位置，不重建输入节点或丢失草稿。
- 默认窗口、最小窗口和窄窗口下，居中整体允许随可用高度滚动，不能把输入按钮挤出可见区域；窄窗口收缩侧栏而不是直接隐藏工作区上下文。

### 工作区侧栏

- 侧栏固定在左侧，使用比主内容略深的中性背景和细右边界，作为工作区上下文的稳定锚点。
- 品牌行采用纯文字布局，只显示 `Agent Desktop`；不使用 Logo（品牌图形）、副标题或没有真实功能的下拉箭头。
- 品牌行垂直节奏保持紧凑：侧栏顶部留白为 16px，品牌行最小高度为 28px，品牌行到“工作区”标签的间距为 20px；窄窗口沿用同一顶部节奏。
- 侧栏只展示当前产品、视频剪辑工作区、当前任务和本地运行状态；当前 MVP 不在侧栏中实现会话列表、搜索、设置或工作区切换。
- “当前任务”在空闲和完成后不显示伪操作或伪状态；仅在任务真实执行期间显示“进行中”。
- 侧栏信息密度高于主对话区，但不使用大面积卡片或高权重品牌装饰；窄窗口只保留图标锚点和当前任务状态。

### 宽度轴与留白

- 对话容器最大宽度为 840px，桌面左右内边距为 32px。
- 输入区最大宽度为 720px；桌面窗口中保持比对话阅读轴略宽的紧凑比例，形成稳定的共享中心轴。
- 560px 及以下窗口将主要左右内边距收紧为 16px。
- 普通消息、工具区和 Agent 回复之间使用 20px 主节奏。不得用 28px 以上的大间距把一次任务拆成互不相关的文档章节。
- 空白用于保证阅读和扫描，不使用固定大高度、空卡片或装饰块填充工作区。

## 对话层级

### 用户任务

- 用户任务右对齐，不显示“你”标题和圆形头像。
- 任务正文使用浅中性背景的气泡，圆角 20px，内边距为上下 9px、左右 15px。
- 气泡宽度不超过对话宽度的 70%，同时不超过 560px；窄窗口可放宽到 86%。
- 已提交附件位于气泡上方并右对齐，使“输入文件”和“任务文字”成为同一用户动作。

### 智能体回复

- 智能体回复保持平面正文，不使用对称聊天气泡。
- 角色标记为 16px 轻量图形，角色文字为 12px 次要层级；它只建立归属，不充当头像。
- 正文使用 14px 字号和 1.65 行高，最大宽度为 760px。
- 处理态、失败态和成功回复沿用同一正文轴；失败使用错误语义色，不增加大型警告卡片。

## 输入区

- 输入区使用 22px 圆角、轻描边和柔和阴影，与页面保持同色表面。
- 文本输入从单行 30px 高度起步，通过内容自动增长，最大高度为 128px；不暴露手动缩放手柄。
- 添加附件按钮固定为 28px 圆形，内部使用居中的 14px SVG 加号；悬停时圆形背景明确加深。发送按钮固定为 34px 圆形，二者分别位于左下和右下。
- 发送按钮是唯一高权重操作，使用蓝色主操作色；不可发送时降低透明度，但尺寸和位置不变。
- 空文本或处理中按钮保持禁用；没有视频但有文字时按钮可用，提交的用户消息不显示空附件标签。
- 常态不显示“就绪”。处理任务时可以在发送按钮旁显示低权重的“处理中”。
- 任务成功后清空草稿但保留当前视频集合，任务失败后保留草稿，方便修改或重试。

## 附件

- 附件使用从 DeepSeek Harness（参考客户端，DSH）文件卡片收紧后的 180×52px 结构，0.5px 边界、12px 圆角；一次任务可分一次或多次选择多个视频，后续选择追加到现有集合。
- 视频图形占 24px，文件名使用 13px 中等字重，下一行使用 11px 弱化文字显示“视频”。
- 长文件名保持单行并显示省略号，不能扩张卡片或遮挡取消按钮；完整文件名通过卡片标题提供。
- 多个附件以 8px 间距横向并排，超出输入区后横向滚动，不换行增加 Composer 高度。
- Composer（输入区）中待提交附件的右侧垂直居中位置提供 16px 圆形取消按钮；桌面端悬停或键盘聚焦时显示，触摸设备常显。点击后必须同步移除 Renderer（渲染层）和 Electron Main（主进程）中的对应视频。
- 已提交附件使用相同文件卡片结构，但不提供取消或预览操作。
- `+` 附件按钮不显示蓝色焦点外圈；键盘焦点仍可到达按钮，但视觉权重保持为轻量圆形控件。

## 工具执行区

- 工具区标题行最小高度为 28px；展开后的每个工具行最小高度为 30px。
- 每行依次显示状态符号、中文动作名、技术工具名、执行状态和耗时。
- 中文动作名与技术工具名在空间允许时保持同一行；状态和耗时靠右，便于纵向扫描。
- 行本身不使用卡片边框，只在悬停时显示轻背景。
- 处理中保持展开；完成后默认折叠为工具数量摘要，并允许用户重新展开。
- 5 至 10 个工具同时展示时仍应在默认窗口中保持紧凑，不得让单行信息变成多层面板。

## 产物区

- 产物是智能体回复的一部分，使用带顶部轻分隔线的结果行，不使用四周边框卡片。
- 视频图形固定为 28px；文件名和“视频 · 已完成”形成主次两级信息。
- “打开文件”是文字型次要操作，保持可见但不与发送按钮竞争视觉权重。
- 窄窗口允许打开动作换到文件信息下方，但不得与文件名或图形重叠。

## 主题与图形

- 页面使用白色基础背景、中性灰文字与边界、蓝色主操作、绿色成功状态和红色失败状态。
- 颜色的具体实现由 `apps/desktop/src/renderer/styles.css` 中当前使用的语义变量负责；本文不复制 HEX 值。
- 不使用大面积单色渐变、装饰光斑、嵌套卡片或品牌插画。
- 当前少量图形不构成引入组件库的理由。若未来真实界面需要统一图标集合，必须先说明消费者与依赖价值，并遵守工程基线。

## 状态验收矩阵

每次影响布局、间距、排版或组件结构时，按本次修改的风险覆盖以下真实状态：

```text
State                        中文状态          验收重点
Empty                        空状态            欢迎内容和输入区整体居中，页面只有一个可用输入区。
Active conversation          活跃对话          空状态消失，同一输入区回到底部，对话进入阅读轴。
Attachment selected          已选择附件        180×52px 文件卡片横向排列，多次选择持续追加且取消行为真实有效。
Processing                   处理中            草稿禁用、状态清楚、布局尺寸保持稳定。
Failure                      失败              错误可读，草稿保留，不出现大型警告面板。
Completed collapsed          完成并折叠        用户任务、工具摘要、回复和产物层级连续。
Completed expanded           完成并展开        5 至 10 个工具仍紧凑，状态与耗时可扫描。
Narrow viewport              窄窗口            文件名、工具状态、产物动作和按钮互不遮挡。
```

桌面主验收尺寸使用接近默认窗口的 1100×750；同时确认应用默认 1120×760 和最小 760×600 下没有结构性问题。涉及 560px 响应式规则时，再补充窄窗口检查。

## 验证流程

自动验证使用项目统一入口：

```bash
corepack pnpm check
corepack pnpm desktop:build
```

视觉验证必须启动正确的应用：

```bash
corepack pnpm desktop:dev
```

开发验收使用 `desktop:dev`，这样 CSS 和 React 修改会即时反映到窗口；生产构建验收使用 `pnpm desktop`。不得直接启动裸 `electron.exe`。确认窗口标题、侧栏、滚动区域和输入区均属于 Agent Desktop，而不是 Electron 默认欢迎页。

测试只验证用户可观察行为，不锁定颜色 HEX、CSS class、像素截图或具体 DOM 层级。视觉验收通过必须来自真实渲染观察，不能由测试或构建通过代替。
