# 第五阶段：Windows 加密凭据持久化修复

本记录对应 `codex/phase5-integration` 的 C2 增量，修复范围为模型、插件、独立 MCP 配置和 OAuth 令牌的现有加密保存链。没有新增依赖、明文凭据副本或主密钥备份机制。

```text

Safe Storage               系统安全存储      Electron 使用操作系统保护的主密钥加密凭据。
Local State                浏览器本地状态    Windows 首次启动的加密主密钥存放在此文件。
Durability                 持久化保证        保存成功后强制退出仍可用同一配置目录恢复。
```

## 真实缺陷与最小修复

Electron 44 的 Windows 全新配置目录中，`safeStorage.encryptString` 已返回密文，但内置浏览器约十秒后才把 `os_crypt.encrypted_key` 写入 `Local State`。此前 SQLite 先提交密文，立即强制终止后没有原主密钥，下一次启动无法解密。尝试异步加密接口也没有改变落盘顺序。

`safe-storage.ts` 复用原系统加密接口，先建立目录监视，再读取实际主密钥字段。已有有效密钥立即返回；新目录等待文件变化并重读，在二十秒期限内确认字段存在后才允许 SQLite 提交。文件事件本身不算成功；文件损坏、非缺失读取错误和期限到达均明确失败，并关闭监视与计时器。模型、插件、独立 MCP、OAuth 及其实际 IPC 调用链均等待该结果。

独立第二轮审查另复现设置覆盖问题：模型密钥等待期间保存主题和记忆设置，旧模型保存快照会覆盖它们。修复把密钥等待放在读取设置之前，等待后读取最新记录并同步合并提交，不增加锁或队列。

## 准确 Windows CI 暴露的短路径缺陷

`3648715667a74b033883c86fb91b057e4a6fa7e8` 的 Ubuntu 工程与构建通过，但 Windows 作业 `114814598486` 在 `fs-event.c:72` 原生断言后终止一个工作进程，只完成 84 个文件、963 项测试；不能把它写成通过。

实际 NTFS 短路径反证在独立子进程重现：原 `waitForSafeStorageKey` 和原生短目录监视均退出 `3221226505`，相同目录解析成长路径后原生监视正常。用户指定短路径配置目录也可到达，因此没有只修改测试临时目录掩盖生产问题。最小修复先对监视目录调用 `realpath`，再建立监视，字段读取仍在建立监视之后，原二十秒期限和加密保存边界不变。

修前证据 `logs/phase5-integration/safe-storage-short-path-1791809907970/evidence.json` 保留；修后 `safe-storage-short-path-investigation-after.log` 的相同短路径生产子进程退出 0。新增 Windows 实际短路径子进程回归，避免旧原生缺陷终止测试宿主；目录解析成为异步操作后，现有文件事件及期限测试等待其真实准备完成。四套专项现在 89/89 通过。最终安装包和双系统结果以重新构建后的总报告为准，旧安装身份不能证明本增量。

## 限制与回滚

这些证据使用真实 Electron 和生产 SQLite 消费者，但不是 NSIS 安装版证据；安装版完整回归单独记录。此前已丢失主密钥的孤立密文无法恢复，本修复防止新的成功保存再发生该问题，不能宣称修复了旧孤立密文。

回滚代码应在候选分支以反向提交执行；不得单独恢复旧凭据保存顺序。数据回滚必须使用与旧应用匹配的完整隔离配置目录备份，包括 `Local State` 与 SQLite。不能只恢复数据库或把其他目录的主密钥拼接进来。
